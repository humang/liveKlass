# E-commerce Event Analytics Pipeline

Python 기반 이벤트 생성기와 PostgreSQL 저장소, Streamlit 대시보드로 구성된 E-commerce 유저 행동 로그 수집 및 분석 파이프라인입니다. 데이터를 적재하는 것에 그치지 않고, 수집된 데이터를 통해 유저의 이탈 원인을 파악하고 서비스 개선을 위한 액션 플랜을 도출하는 것을 목표로 설계했습니다.

## 기획 의도 및 데이터 수집 전략

단순히 "페이지 조회 수 100회, 구매 10회"와 같은 단편적인 지표는 마케팅 팀이나 기획자에게 구체적인 개선 방향을 제시하지 못합니다. 유저가 사이트에 들어와서 왜 구매하지 않고 이탈했는지 그 원인을 진단하기 위해, 본 프로젝트는 시간에 따른 이탈률 분석에 초점을 맞추었습니다.

1. 수집하는 핵심 데이터
개별 이벤트를 독립적으로 수집하지 않고, 유저의 1회 방문을 의미하는 세션(session_id)을 기준으로 데이터를 묶어 수집합니다. 각 세션 내에서 발생하는 행동(page_view, search, item_click, purchase)과 해당 이벤트가 발생한 정확한 시간(timestamp)을 기록합니다.

2. 데이터가 가지는 의미
수집된 세션 내의 첫 이벤트 시간과 마지막 이벤트 시간의 차이를 계산하여 유저의 체류 시간을 구하고, 세션 내 발생한 이벤트 개수를 통해 유저의 탐색 깊이를 측정합니다. 이를 통해 유저를 즉시 이탈자, 아이쇼핑 유저, 목적형 구매자 등으로 분류할 수 있습니다.

3. 기대되는 결과 및 액션 플랜
이 데이터를 대시보드로 시각화하면 실무 부서는 다음과 같은 구체적인 액션을 취할 수 있습니다.
- 체류 시간이 10초 미만인 즉시 이탈자가 많을 경우: 외부 타겟팅 광고와 랜딩 페이지의 연관성을 점검하고 메인 화면의 UI 로딩 속도를 개선합니다.
- 탐색 횟수가 많고 체류 시간이 길지만 구매하지 않은 유저가 많을 경우: 가격이나 배송비에 대한 허들이 있다고 판단하여 해당 유저들에게 할인 쿠폰 팝업을 띄우는 등 적극적인 리타겟팅 마케팅을 실행합니다.

## 기술 스택 및 선정 배경

위에서 정의한 시간 기반의 이탈률 분석이라는 목적을 가장 효율적으로 달성하기 위해 아래의 기술을 선택했습니다.

1. 언어: Python
Java나 Go는 대규모 동시성 처리에 유리하지만, 본 프로젝트의 핵심인 세션 기반의 복잡한 로그 가공 및 시각화 영역에서는 Pandas, Streamlit 등 데이터 생태계가 풍부한 Python이 가장 적합하다고 판단하여 파이프라인 전체를 단일 언어로 구성했습니다.

2. 저장소: PostgreSQL
이벤트 로그는 형태가 유동적이라 NoSQL을 활용하는 경우가 많으나, 과제의 명확한 필드 설계 요구사항을 충족하기 위해 관계형 DB를 채택했습니다. 특히 본 파이프라인의 핵심인 세션별 체류 시간과 탐색 깊이를 분석하려면 복잡한 시계열 그룹화 연산이 필요한데, RDBMS 중 윈도우 함수 기능이 가장 강력한 PostgreSQL을 선택하여 통계 및 집계 쿼리 성능을 최적화했습니다.

## 실행 방법

1. 필요한 도구
- Docker 및 Docker Compose가 시스템에 설치되어 있어야 합니다.

2. 실행 명령어
프로젝트 루트 디렉토리에서 아래 명령어를 실행하여 파이프라인 전체(DB, 이벤트 생성 앱, 대시보드)를 백그라운드에서 실행합니다.
docker compose up -d --build

3. 확인 방법
컨테이너가 정상적으로 실행된 후, 브라우저에서 http://localhost:8501 주소로 접속하면 Streamlit 기반의 인터랙티브 데이터 분석 대시보드를 확인할 수 있습니다.

## 프로젝트 구성 및 파이프라인 상세

- main.py : 세션 기반 이벤트 생성기 애플리케이션
- app.py : Streamlit 기반 데이터 분석 및 시각화 대시보드
- init.sql : PostgreSQL 테이블 및 인덱스 초기화 스크립트
- k8s/ : Kubernetes 프로덕션 배포용 매니페스트 폴더

1. 이벤트 생성기 (main.py)
단순 무작위 데이터 생성을 피하고 이탈률 분석의 실효성을 높이기 위해, 3가지 페르소나에 가중치를 두어 이벤트를 생성하도록 설계했습니다.
- bouncer : 1~2개의 page_view만 발생 후 짧은 시간 내 세션 종료
- window_shopper : 검색, 클릭 등을 다수 탐색하지만 구매 없이 세션 종료
- purchaser : 검색 및 클릭 후 purchase 이벤트로 전환되는 유저

2. 스키마 설명 (init.sql)
JSON 통째 저장을 지양하고, 다양한 이벤트 타입(검색, 클릭, 구매)을 단일 테이블에 통합하되 이벤트별 특화 필드는 Nullable로 설계하여 유연성과 분석 속도의 균형을 맞추었습니다. 특히 session_id와 timestamp 컬럼을 분리하여, 분석 시 복잡한 조인 없이 SQL의 윈도우 함수만으로도 체류 시간과 탐색 깊이를 고속으로 집계할 수 있게 설계했습니다.

## 프로덕션 환경 확장 전략 (Kubernetes 아키텍처)

현재는 실행 편의성을 위해 Docker Compose 환경으로 구성했으나, 실제 대량의 로그 트래픽이 발생하는 프로덕션 환경을 가정하여 k8s 폴더에 배포 매니페스트를 설계했습니다.

1. 데이터베이스 영속성 보장 (StatefulSet & PVC)
DB를 일반 Deployment로 배포할 경우 파드 재시작 시 데이터가 소실되는 문제가 있습니다. 이를 방지하기 위해 PVC로 영구 볼륨을 마운트하고, 안정적인 네트워크 식별자를 유지하는 StatefulSet으로 PostgreSQL을 구성했습니다. (만약 로그 데이터가 RDBMS로 감당할 수 없을 만큼 누적된다면, S3 데이터 레이크와 Redshift를 결합한 아키텍처로 분리할 계획입니다.)

2. 트래픽 라우팅 및 자동 확장 (Gateway API & HPA)
외부 통신은 기존 Ingress의 한계를 극복한 최신 라우팅 표준인 Gateway API를 사용하여 이벤트 수집 API와 대시보드 요청을 분리했습니다. 또한 트래픽이 몰릴 경우를 대비해 CPU 사용률 기반으로 앱 파드를 자동 확장하는 HPA 리소스를 추가했습니다.

3. 보안 및 설정 분리 (Secret)
Docker Compose 구성에서는 편의상 환경변수에 DB 비밀번호를 하드코딩했으나, K8s 환경에서는 이를 방지하기 위해 ConfigMap과 Secret을 분리하여 보안성을 높였습니다.

## 구현하면서 고민한 점

1. 마케팅 액션을 이끌어낼 수 있는 의미 있는 로그 데이터란 무엇일까?
초기에는 Faker 라이브러리로 이벤트 타입만 무작위로 생성했습니다. 하지만 이 데이터로는 대시보드를 만들어도 사이트를 어떻게 개선해야 할지 파악하기 어려웠습니다. 이에 대한 해결책으로 유저 행동을 세션 단위로 묶고 페르소나 행동 패턴 모델링을 도입했습니다. 그 결과 대시보드에서 체류 시간 대비 전환율을 파악할 수 있게 되었고, 짧은 시간 내 이탈하는 유저가 많으면 랜딩 페이지를 개선해야 한다는 실질적인 인사이트를 도출할 수 있었습니다.

2. 분석 결과를 가장 효과적으로 전달하는 시각화 방법은 무엇일까?
처음에는 Matplotlib을 사용해 분석 결과를 정적인 이미지 파일로 저장했습니다. 하지만 실제 업무 환경에서 데이터 분석 결과를 공유할 때 정적 이미지는 탐색적 데이터 분석에 한계가 명확하다고 생각했습니다. 이를 해결하기 위해 Python 기반의 Streamlit과 Plotly를 도입했습니다. 별도의 무거운 BI 툴을 세팅하지 않고도 인터랙티브 조작이 가능한 실무 수준의 대시보드를 구축할 수 있었습니다.

3. 시스템 모니터링에 대한 고려
단순히 앱을 배포하는 것에서 끝나지 않고, 배포 이후의 시스템 안정성을 고려해야 한다고 판단했습니다. 이를 위해 Kubernetes Deployment 파일의 파드 템플릿에 Prometheus 스크랩 어노테이션을 추가하여, 향후 메트릭 수집 및 Grafana 연동을 통한 시스템 모니터링이 가능하도록 기반 설계를 반영했습니다.
